Architectural constraints

These held for the whole build. Deeper detail lives in architecture.md (§17 for the gateway as built, §19–20 for the endpoint agent and kernel), docs/FLEET_PLATFORM.md and docs/BENCHMARK.md.

Constraint 1

Not a CLI-only script

An enterprise-grade AI-EDR (AI Endpoint Detection & Response) inline guardrail platform, not a narrow local hook.

Constraint 2

Universal target ecosystem

Commercial LLMs (ChatGPT, Gemini, Claude); AI coding IDEs and agents (Claude Code, Gemini CLI, Antigravity IDE, Claude IDE extensions, coding and MCP agents); Samsung FabriX and Samsung AI Pro (aipro).

Constraint 3

The 4-stage flow with the Falcon technique

Attack vector ingestion → AI Risk Database → AI-EDR Security Guard with Falcon → clean safe input to the AI Brain, or the Quarantine Vault.

Constraint 4 · added 31 Oct 2026

Guard the machine, not only the request

An endpoint agent, CheckPoint Zero (checkpointd), checks what AI agents do on each laptop or server, with kernel checkpoints where the OS allows (§7).

§1Reference architecture: the AI-EDR inline model

The platform applies the AI-EDR (Artificial Intelligence Endpoint Detection & Response) paradigm to stop both direct and indirect prompt injection before the target LLM, "the AI Brain", processes a token.

Stage 2 · Threat data

AI Risk Database

  • Known jailbreak signatures and hashes
  • Vector embeddings of attack prompts
  • Falcon threat intel and IOC feeds
Lookup + sync

Stage 1 · Attack vectors

Direct and indirect

A. Direct: the active user types “ignore previous rules and do X”.

B. Indirect: poisoned PDFs, résumés, docs, RAG chunks and web scrapes, e.g. hidden white text saying “ignore…”.

Stage 3 · Security Guard

Inline pre-LLM guardrail + Falcon engine

  1. Checks for hidden tricks: steganography, invisible text, Base64/hex, PDF metadata
  2. Strips out bad commands: surgical sanitization (CDR)
  3. Validates against the AI Risk Database
  4. Executes the Falcon technique
ALLOWED · clean safe input

Stage 4 · The AI Brain

ChatGPT · Gemini · Claude · FabriX · AI Pro receive sanitized, verified context. Safety rules stay intact and the answer is helpful and safe.

BLOCKED · malicious input

Trap & Quarantine Vault

Payload isolated with 0 LLM tokens spent, forensic snapshot logged, SIEM / SOC alert emitted. The Falcon Loop updates the AI Risk Database.

As built

The same four stages run in three places:

  • The gateway: the reverse proxy and the hook API.
  • Its clients: IDE hooks, the browser extension, and the SDK and Samsung examples.
  • The endpoint agent: it embeds the same engine on each machine (§7).

§2The Falcon technique

The Falcon technique is a core pillar of the guardrail, implemented in two complementary layers.

Layer A · Falcon-style lightweight sensor and behavioral runtime interception

Inspired by the CrowdStrike Falcon EDR architecture, the guardrail uses a dual sensor and cloud threat graph model instead of brittle static regexes or heavy external proxies.

Lightweight inline sensor hook

Sits at the LLM API (proxy), the IDE hook (prompt submit, before and after each tool call), the browser and the MCP tool boundary. It observes user prompts and agentic process trees: prompt → RAG retrieval → tool selection → sub-agent spawn.

Behavioral IOAs over static IOCs

Even a zero-day paraphrase that no regex knows is caught by intent: instruction-override semantics, role-play framing, privilege escalation, or an abnormal file-to-prompt transition.

As built · sensor
  • Added latency is p50 17 ms and p95 60 ms per prompt on a laptop CPU, mostly from Tier 2.
  • The endpoint agent adds a sensor on the machine itself. On Linux that sensor is a real eBPF kernel program (§7).

The Falcon Loop: real-time threat graph feedback

Whenever a malicious prompt or poisoned PDF is trapped, its semantic embedding and structural signature are pushed back into the AI Risk Database, immunizing ChatGPT, Gemini, Claude, Samsung FabriX and AI Pro across the organization.

As built · Falcon Loop
  • The gateway learns in-process at once: the offending text and each instruction sentence become signatures and vectors, and the trie is rebuilt in under 1 ms.
  • Segments with DLP findings (secrets, PII, proprietary markers) are never promoted.
  • Learned entries also go to the persistent AI Risk DB in the control plane, and reach endpoints only through gated, signed releases (§8).

Layer B · FALCON fast-adaptive local classification and sanitization

To stay inline-fast without asking a large, expensive LLM to guard another LLM, the Falcon engine runs a three-step micro-pipeline:

  1. De-obfuscation and hidden-trick unpacking

    Extracts text from PDFs, DOCX and source code, and flags any mismatch between what is rendered and what is parsed: white-on-white text, zero-width Unicode, font size 0, PDF metadata or annotation injections, Base64/ROT13 payloads.

  2. Surgical command stripping (CDR)

    In Strip/Sanitize mode, an injected command inside a legitimate document is neutralized while the clean data is kept, so the workflow does not break. High-severity threats go to hard quarantine.

  3. Fast local sequence classification

    A local model next to a fast vector similarity lookup against the AI Risk Database.

    As built · model
    • Model: protectai/deberta-v3-base-prompt-injection-v2 on ONNX Runtime (Apache-2.0, ~740 MB, fetched by scripts/download_model.sh), cascaded behind a local hashed n-gram model.
    • Short texts are scored whole.
    • Long texts: the local model picks the 16 most suspicious windows and DeBERTa scores them in one batch. DeBERTa never scores raw code.
    • Korean and fragments under 5 words use the local model, because DeBERTa is English-only.
    • Corroboration cap: in untrusted content, a classifier-only signal with no IOA, signature, vector or hidden-layer corroboration is capped at LOW. Without the cap, 70% of real source files were flagged.

§4The four stages

Stage 1 · Attack surface collectors

  • Direct attack collector: captures active user prompts from chat UIs, IDE chat boxes and API calls.
  • Indirect attack and file-poisoning inspector (IndirectFileScanner): covers the poisoned-PDF-résumé vector. It parses PDFs, Word documents, Markdown, HTML and source code before they enter the LLM context window.

Hidden-trick detectors

  • Visual vs. text-layer diffing: text in the PDF stream with font_size <= 1pt, opacity 0, rendering mode 3 (invisible), or foreground color equal to the background (#FFFFFF on #FFFFFF).
  • Unicode smuggling and homoglyphs: Unicode tag characters (U+E0000–U+E007F), zero-width joiners, bidirectional overrides (U+202E).
  • Metadata and comment injection: PDF /Info dictionaries, XMP metadata, HTML comments and code comments that carry imperative LLM instructions.
As built

PyMuPDF and pdfplumber for PDF, python-docx for Word. Results are cached by content hash: a 20 KB file costs p50 226 ms on the first scan and nothing after.

Stage 3 · The Security Guard (inline guardrail + Falcon engine)

When a CanonicalAIEDRRequest arrives, the Security Guard runs three operations.

1 · Checks for hidden tricks (HiddenTrickAnalyzer)

Structural anomalies, invisible PDF text, encoded payloads (Base64, hex, ROT13) and token-splitting attacks.

2 · Validates against the AI Risk Database with the Falcon technique (FalconThreatEvaluator)

TierWhat it doesAs built
Tier 1 · deterministicAho-Corasick and regex scan against the Risk DB, plus the secret and PII DLP scannerUnder 2 ms
Tier 2 · Falcon classifierIn-memory ONNX classification gives an injection_probability_score from 0.0 to 1.0, alongside behavioral IOAs (e.g. untrusted data issuing orders to the system role) and the agent process treeDeBERTa-v3 cascade (§2, Layer B); threshold 0.80; median about 17 ms per prompt
Tier 3 · semantic matchCosine similarity to known and Falcon-learned attack vectors catches polymorphic variantsτ = 0.80 with the hashing embedder (the plan's 0.88 is for a neural embedder); under 5 ms
Similarity(Einput,Erisk_db) = Einput·Erisk_db ‖Einput‖‖Erisk_db‖

Flagged as a variant of a known attack when Similarity ≥ τ.

Scoring, set per tenant in config/ai_edr_policies.yaml:

  • Weights: classifier 0.55, IOA 0.35, anomaly 0.10.
  • Severity bands: LOW 0.30, MEDIUM 0.50, HIGH 0.70, CRITICAL 0.90.
  • DLP: secrets BLOCK; PII and proprietary markers AUDIT.
  • Detector errors fail CLOSED by default.

3 · Strips bad commands, or blocks and quarantines (DecisionAndRemediationEngine)

Path A · malicious input → BLOCKED, trapped

  • A direct attack or high-severity indirect injection short-circuits the request at once.
  • The payload goes to the Quarantine Vault with full forensic metadata: user ID, file hash, matched signature, Falcon IOA score.
  • The AI Brain is never called: 0 tokens spent.

Path B · recoverable injection → STRIPPED, allowed

  • Under STRIP_AND_SANITIZE, the hidden or malicious spans are removed from the document.
  • The rest is wrapped in spotlighting delimiters, <untrusted_document_content>…</untrusted_document_content>.
  • The clean, safe input goes on to the AI Brain.
As built
  • STRIP mode strips indirect findings up to max_strip_severity (default CRITICAL), and blocks if the re-scan still scores 0.7 or more.
  • The Quarantine Vault is SQLite plus a JSONL SIEM sink in CEF style.
  • Analysts confirm or release payloads in the SOC console (/console).

Stage 4 · The AI Brain (protected downstream LLM)

  • Only clean, safe input reaches ChatGPT, Gemini, Claude, Samsung FabriX or Samsung AI Pro.
  • Because hidden tricks and override commands are stripped or blocked first, the model's safety rules stay intact and it returns a helpful, safe answer.
As built

For demos without API keys, src/mock_llm/vulnerable_brain.py is a deliberately gullible model that obeys injected instructions and speaks all five wire formats. Calling it directly shows what happens without AI-EDR.

§7Endpoint agent and kernel checkpoints (CheckPoint Zero)

Hooks and extensions protect the tools that use them. The endpoint agent protects the machine, including AI tools that have no hooks.

checkpointd runs on each machine with the detection engine embedded. It makes no cloud call and works offline. It judges only processes descended from an AI agent: by default claude, gemini, cursor, aider, codex, copilot, ollama and similar, changeable with --ai-process.

CheckpointBehaviour
ExecRebuilds the lineage of every new process and judges commands in POSIX and Windows forms (%USERPROFILE%, $env:USERPROFILE, curl.exe, PowerShell download cmdlets):
  • Credential path + network tool → CRITICAL TOOL_HIJACK
  • Credential read → SECRET_ACCESS
  • Destructive commands, Windows included (shadow-copy deletion, wbadmin, bcdedit, cipher /w) → block
  • Download-or-execute abuse of certutil, bitsadmin, mshta, regsvr32, rundll32 → alert
  • Anything else → the full pipeline, as a tool call
ENFORCE mode kills the process tree.
FilePre-scans documents in watched workspaces. A poisoned file is moved to quarantine and <name>.sanitized.txt is written in its place
EgressAI-lineage connections outside the allow-list (LLM APIs, GitHub, package registries, private ranges) → alert, or kill with --block-egress
ContentEd25519-signed Risk DB bundles are verified (signature and SHA-256) and hot-swapped; on any failure the last good bundle is kept
SafetySafe mode (monitor only) after 2 unclean exits; fail-open on detector errors; offline outbox with idempotent event IDs

§8Control plane, content pipeline and portal

The control plane (src/control_plane/, mounted at /v1/cp in the gateway app) handles agent enrollment, heartbeat and telemetry, and releases Risk DB content through a fixed pipeline:

  1. SnapshotFreeze the current Risk DB entries.
  2. Quality gateReplay 35 attacks (EN + KO) and 40 benign texts. Fail on any false positive, recall under 85%, or a recall drop over 5 points.
  3. SignEd25519 signature per tenant.
  4. Ring rolloutCANARY → EARLY → BROAD → GA.
  5. Auto-rollbackWhen 2 or more agents report a content failure.
  • Learning loop: gateway promotions become tenant-tier LEARNED entries. Auto-release builds, gates and promotes them to CANARY only.
  • Portal (/portal): overview; detections with process lineage; endpoints with ring and mode control; Risk DB with OWASP/ATLAS mapping, where analysts approve, disable or mark false positives; releases with gate, promote and rollback; deploy; audit log.

§10Known limits

  • Inputs only: model output is not inspected yet.
  • Indirect-attack recall on new phrasings (33%) and Korean coverage are the main gaps. The next step is a multilingual classifier.
  • Redis and Qdrant run as in-process stand-ins, and SQLite stands in for Postgres. There is one control-plane node and no SSO or RBAC on the portal yet.
  • The Windows driver has never been loaded. It needs test signing or attestation signing and a Microsoft-assigned altitude. Windows egress is still checked in user space (the production path is a WFP callout), and the Windows agent is not yet a protected (PPL) service.
  • The Linux kernel checkpoint needs bpf in the active LSM list, which Ubuntu does not enable by default. Egress denial covers IPv4 only.
  • The FabriX and AI Pro request formats are assumptions until Samsung provides the official schemas.
